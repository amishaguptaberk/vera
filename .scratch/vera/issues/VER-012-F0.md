Title: VER-012-F0 — Next.js scaffold, tokens and parity harness

User value:
The team has a running Next.js app with Vera's exact tokens and an automated way to prove each screen matches the prototype.

Scope:
- Next.js App Router project with TypeScript strict, lint import boundaries per the architecture doc §3, CSS Modules and tokens from Handoff §9.
- Fonts and base styles; API rewrite to the backend; generated types pipeline.
- Parity harness that serves the prototype and the app, drives both to a named state and compares screenshots at 1440, 1200, 900 and 390 px, with a states manifest.
- Follow docs/frontend-architecture.md for layer rules, state ownership and parity method; the prototype is the visual reference and is not redesigned.

Non-goals:
- Any real screen.
- Business logic in the client (step, policy, closure, action gating).
- Visual or copy changes from the prototype.

Acceptance criteria:
- The app builds and serves a placeholder route using the tokens.
- The lint rule fails a build when a presentation component imports the API layer.
- The harness passes on one trivial state and fails when a token value is deliberately changed.
- Token values equal Handoff §9 exactly.

Dependencies:
- None

Test-first behavior:
A parity test for the one trivial state.

Demo proof:
Run the harness and show a pass, then a deliberate failure.

References: docs/backend-implementation-plan.md, docs/spec/Vera_Handoff.md, docs/spec/Vera_ToSpec.md, docs/spec/Vera_User_Stories.md
Paths, symbols, nearest tests and commands are discovered by the scout before the builder contract is written.
