Title: VER-006 — OTP and push identity verification

User value:
Before any call, Priya proves she controls the approved channel, and Sam sees only the verification status — never the code.

Scope:
- identity_verifications and verification_attempts; states per plan R4.
- Commands: send_verification_request, resend_verification_request (cooldown), cancel_verification_request, expire_verification_request, submit_otp, answer_verification_push; keys for cancel and expire (gap G1).
- Simulated verification adapter with a cardholder-only outbox; verification_expirer job.
- `POST /api/verifications/{id}/submit_otp` and `/answer`; identity detail in Communications; labeled synthetic-demo controls that act as the cardholder.

Non-goals:
- Callback.
- Any change to the policy outcome from verification.

Acceptance criteria:
- The raw code is never stored; only an HMAC is persisted.
- No analyst response, event payload or log line contains the code; analyst submit_otp returns 403 (fixture 42).
- A correct code or an approved push moves the step to `verify` and leaves policy outcome unchanged (fixtures 25, 43).
- Three wrong codes lock the request; the analyst sees Verification failed with follow-up, reassign and hold as recovery; the case is not closed (fixture 26).
- Expiry is recorded once; resend inside the cooldown returns 429; a new send uses a new key (fixture 27).
- A denied push shows Verification denied with another method available and is not treated as fraud (fixture 28).
- Verification events are attributed to the cardholder role.

Dependencies:
- VER-005

Test-first behavior:
A test that sends a request, submits three wrong codes as the cardholder and asserts the locked state, three code_rejected events with role cardholder, and the analyst's available actions.

Demo proof:
Send the request as Sam, enter the code in the cardholder view, and show Sam's card change to Identity verified.
